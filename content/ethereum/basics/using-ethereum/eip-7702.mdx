**EIP-7702** lets a regular account, the kind controlled by a private key (an EOA), **delegate** to the code of a [smart contract](../how-it-works/smart-contracts.mdx). The account keeps its address, balance and history, but gains the abilities of a [smart wallet](./smart-wallets.mdx): bundling several actions into one transaction, having someone else pay the gas fee, signing with a passkey.

EIP-7702 has been live on mainnet since the Pectra upgrade, on May 7, 2025.

## Why is it needed?

Before EIP-7702, if you wanted a smart wallet, you had to create a new contract account, for example following [ERC-4337](./erc-4337.mdx). A new account has a new address, so you had to move your assets over one by one, pay a fee for each transfer, and tell everyone your new address. That's why most users stayed with regular accounts.

EIP-7702 lets a regular account use a contract's code right at its old address, with no need to move house.

## How does it work?

<DelegationScene />

1. **Sign an authorization.** The account's private key signs an **authorization** containing three things: the address of the contract whose code you want to use, the network's ID number (chain ID), and the account's [nonce](../how-it-works/digital-signatures.mdx#nonce-each-transaction-runs-only-once).
2. **Send it in a type 4 transaction.** The authorization travels in a new kind of transaction called a type 4 transaction (set code transaction). Whoever sends the transaction doesn't have to be the account owner: another party can send it and pay the gas fee on their behalf.
3. **Write the pointer.** The network writes a **pointer** to the contract into the account (the delegation designator): the three bytes `0xef0100` followed by the contract's address. The code isn't copied; the account just points to it.
4. **Run the code on the account.** From then on, whenever someone calls the account, the network runs the contract's code, but on the account's own balance and data.

A delegation doesn't expire on its own. It stays in place until you sign a new authorization for a different contract, or delegate to the zero address to remove the pointer.

## What can it do?

It depends on the code your wallet uses:

- **Batching.** Approve spending and swap tokens in a single transaction, instead of signing twice. Apps ask for batching through the wallet's standard interface (`wallet_sendCalls`, ERC-5792), not by asking you to sign an authorization.
- **Sponsored fees.** An app or a service pays the gas fee for you, or you pay the fee in another token instead of ETH.
- **Limited secondary keys.** Give an app a secondary key that can only do a few things, for example spend only tokens and not ETH, or interact only with that specific app.
- **Passkeys.** Sign with your fingerprint or face, with the key kept in your phone's secure chip, if your wallet's code supports it.

## The old key still has full control

<Callout type="warn" title="Important">
Delegation doesn't replace your key. The original private key, and the recovery phrase it was generated from, can still sign regular transactions and can still re-delegate to another contract. Rules in the code, such as spending limits or multisig, can't stop that key. As ethereum.org puts it, delegating to a multisig wallet's code doesn't turn the account into a multisig wallet.
</Callout>

With a delegated account, keeping your recovery phrase safe matters just as much as before. If you need rules that are truly binding, such as social recovery or multisig, use a separate contract account under [ERC-4337](./erc-4337.mdx): there, every instruction has to go through the contract's rules.

## Risks to know about

- **Delegating to malicious code means handing over the whole account.** Delegated code runs with full access to all of the account's assets. According to EIP-7702 itself, apps must not ask users to sign authorizations, and wallets shouldn't offer an interface for doing so. Major wallets only allow delegation to a few contracts they have vetted. Any website asking you to "upgrade your account" is a sign of a scam.
- **One authorization can be used on every network.** An authorization with a chain ID of 0 is valid on every Ethereum-compatible network, not just the one you're using.
- **Switching contracts doesn't erase old data.** Data the old contract wrote into the account is still there when you delegate to a different contract. Wallets have to handle this themselves, so only switch through your own wallet app.
- **Scammers use EIP-7702 too.** A few weeks after Pectra, Wintermute's research team reported that more than 97% of authorizations pointed to copies of the same "sweeper" contract, according to [Cointelegraph on June 2, 2025](https://cointelegraph.com/news/wintermute-crimeenjoyor-flags-malicious-ethereum-contracts). These were accounts whose keys had already leaked: scammers delegated them so that any ETH sent in would be swept out automatically. EIP-7702 doesn't leak keys, but if your key has already leaked, don't send anything more to that address.

<Callout type="error" title="Caution">
Only delegate through a feature of the wallet app you actually use. Never sign an account "upgrade", "activation" or "delegation" requested by a website, a message or an unfamiliar link.
</Callout>

## Compared with ERC-4337

| | EIP-7702 | ERC-4337 |
|---|---|---|
| Address | Keeps the old address | New address; you have to move your assets over |
| Original key | Still has full control and can bypass the rules in the code | None: every instruction has to go through the contract's rules |
| Needs a network upgrade? | Yes, since Pectra (2025) | No, it has run as contracts since 2023 |

The two can be used together. A delegated account can delegate to ERC-4337-compatible code, so it can share ERC-4337's infrastructure such as bundlers and paymasters. ERC-4337's EntryPoint contract has supported EIP-7702 accounts natively since version 0.8, in March 2025. See [ERC-4337](./erc-4337.mdx).

## Summary

- EIP-7702 (Pectra, May 2025) lets a regular account delegate to a contract's code, while keeping its address and balance.
- The authorization is signed with the account's key, travels in a type 4 transaction, and stays in place until it is changed or removed.
- The old key still has full control. Rules in the code can't save you if your recovery phrase leaks.
- Only delegate through your wallet app, never through an unfamiliar website.
